Chicago Transit Authority · streaming event pipeline

Where is my train, right now?

The CTA has a sensor on each side of every "L" platform and a turnstile at every entrance. Each one of them is a tiny event generator. This project wires those events into Apache Kafka and turns the stream into a status board that updates while you watch — trains moving from station to station, riders accumulating, weather in the corner.

The shape of the system

Everything meets at the broker

Read it like a transit map. Four kinds of data enter from the left, all of them converge on Kafka, and three of them leave again towards the status board. No producer knows that the dashboard exists, and the dashboard knows nothing about sensors. That is the whole point of putting a broker in the middle.

Stop by stop

Six stages, each feeding the next

Every stage writes to a topic that the following stage reads. That is the only contract between them, which is why you can restart any single piece without telling the others.

01

Arrival producers

Each station owns a Kafka producer. When a train pulls in, the station emits one event saying which train, travelling in which direction, and which station it just left. The events are Avro-encoded, so the schema travels to the Schema Registry once and every message afterwards carries only a four-byte schema id instead of its field names.

in Station.arrive_a() out chicago.transport.arrivals
Why Avro? A turnstile event is three small fields. Sending "station_name" as text with every one of them would cost more than the data. Avro moves the field names out of the message and into the registry: what travels is one magic byte, a four-byte schema id, and the packed values. The consumer looks that id up once and caches it.
02

Turnstile producers

Each station also has a turnstile, driven by real CTA ridership figures: Clark/Lake averages 22,811 weekday entries, and an hourly curve spreads them across the day so the morning peak actually looks like a peak. One Kafka event per rider, no aggregation yet.

in ridership_seed.csv out chicago.transport.turnstile
Why emit raw events? Counting here would freeze one answer into the data. Emitting every entry lets stage 06 count per station, and lets someone later count per hour, or per line, without replaying history.
03

Weather, through REST Proxy

The weather hardware is old and cannot run a Kafka client library. It speaks HTTP, so it posts to Kafka REST Proxy instead, with the Avro schemas inline in the request body and a Content-Type of application/vnd.kafka.avro.v2+json. The proxy does the producing on its behalf.

in POST /topics/… out chicago.transport.weather
Why a proxy? It is the escape hatch for anything that cannot link librdkafka: embedded devices, a shell script, a language with no good client. The cost is an extra hop and no exactly-once semantics.
04

Kafka Connect pulls the station table

Station names, line colours and platform order live in PostgreSQL, not in the event stream. The JDBC source connector polls the stations table once a minute in incrementing mode, tracking stop_id, and republishes each row as a Kafka message. No code to write — the connector is pure configuration.

in jdbc:postgresql://postgres:5432/cta out chicago.transport.stations
Why not just query the database? Then the dashboard would depend on PostgreSQL being up, and so would anything else that needed station names. Copying the table into Kafka once lets every consumer keep its own local view.
05

Faust reshapes the stations

The raw rows carry ten columns, three of which are the booleans red, blue and green. The dashboard wants four fields and a single line colour. A Faust agent consumes the Connect topic, builds the trimmed record, and stores it in a table whose changelog is the output topic.

in chicago.transport.stations out chicago.transport.stations.table
Why a table and not a stream? There is one current answer per station, not a history of them. A changelog-backed table keeps the latest row per key and replays it to any consumer that starts from the beginning.
06

ksqlDB counts the turnstiles

Two SQL statements, no application code. The first declares the turnstile topic as a stream; the second aggregates it into a table grouped by station. ksqlDB keeps the count up to date as events arrive and writes each change back to a Kafka topic.

in chicago.transport.turnstile out TURNSTILE_SUMMARY
Why SQL here? The transformation is a GROUP BY. Writing a consumer, a state store and a producer to express a GROUP BY is a lot of code to maintain for something a query engine already does.

And then the dashboard

A Tornado web server runs four Kafka consumers on its event loop, one per topic, and keeps an in-memory model of the three lines. The HTML page is rendered from that model and refreshes every ten seconds. Nothing is stored; restart it and it rebuilds the whole board by replaying the topics from the beginning.

What runs where

Kafka, Schema Registry, REST Proxy, Connect, ksqlDB and PostgreSQL run in Docker and talk to each other by service name. The Python processes run on your machine and reach the same cluster through localhost. Mixing those two up is the classic first bug: a connector configured with localhost points at the Connect container itself.

Getting it running

Four terminals

First, the infrastructure

Builds the Connect image with the JDBC connector, then starts seven containers. Wait until every service reports (healthy).

docker compose up -d --build
docker compose ps

1 · Producers

Registers the connector, then starts the simulation.

cd producers
python3.13 -m venv venv && . venv/bin/activate
pip install -r requirements.txt
python simulation.py

2 · Faust

Reshapes the station rows into the table the board reads.

cd consumers
python3.13 -m venv venv && . venv/bin/activate
pip install -r requirements.txt
faust -A faust_stream worker -l info

3 · ksqlDB

Creates the turnstile summary table. Runs once and exits.

cd consumers && . venv/bin/activate
python ksql.py

4 · Status board

Then open localhost:8888.

cd consumers && . venv/bin/activate
python server.py
Station and ridership data derived from the City of Chicago Transit Authority open datasets. The simulation is synthetic; no live CTA feed is used.
